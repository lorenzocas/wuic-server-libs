Manuale Introduzione

Manuale FatturazioneElettronica

Guida completa all'installazione, configurazione e uso dell'applicazione FatturazioneElettronica: ciclo attivo (preventivi → ordini → DDT → fatture inviate → SDI), ciclo passivo (ordini acquisto → fatture ricevute via SDI), conservazione sostitutiva, report fiscali (LIPE, Esterometro, CU, comunicazioni periodiche), dashboard analytics e scheduler.

v1.0 production-ready italiano SDI v1.2 CADES‑BES SQL Server + MySQL

Cos'è FatturazioneElettronica

Applicazione di fatturazione elettronica conforme alla normativa italiana (provvedimento Agenzia delle Entrate n. 89757/2018 e successivi). Costruita sul framework WUIC (Web UI Crafter), eredita tutte le funzionalità framework (designer dashboard, report designer Stimulsoft, workflow, scheduler, notifiche real-time, multi-lingua, audit, RAG chatbot) e aggiunge un dominio applicativo completo per la fatturazione.

Caratteristiche principali

  • Ciclo attivo completo: preventivi → ordini di vendita → DDT → fatture inviate, con conversione automatica fra documenti e ricalcolo totali via stored procedure idempotenti.
  • Invio SDI con 5 provider: Direct PEC (gratis, usa la propria casella PEC) + 4 intermediari commerciali a pagamento (Aruba, FatturePEC, Pec.it, Notarify) + Mock per ambienti dev/test. Selezione automatica del provider in base alla sezione Sdi.* configurata in appsettings.json.
  • Firma CADES‑BES con certificato PKCS#12 (qualificato AgID in produzione, self-signed dev tramite scripts/generate-dev-sdi-cert.ps1).
  • Ricezione notifiche SDI automatica via 6 poller (Aruba PEC, FatturePEC, Pec.it, Notarify REST, IMAP generico PEC, PEC italiana). Tracking del cursore di paginazione in sdi_provider_cursor per idempotenza fra restart.
  • Conservazione sostitutiva a norma con 3 provider: Filesystem locale (con timestamp RFC 3161), InfoCert, Aruba. Index immutable+sealed in conservazione_index.
  • Report fiscali XML generati server-side: LIPE (liquidazione IVA periodica), Esterometro, CU (Certificazione Unica), comunicazioni periodiche generiche.
  • Scheduler integrato: invio massivo fatture, polling SDI, generazione report periodici, solleciti scaduti, riconciliazione bancaria. Configurabile via tabella scheduler con action_type SQL / Webservice HTTP / Assembly method / Mailing list.
  • Dashboard analytics: finanze, cash flow forecast, aging crediti/debiti, top clienti, controllo fiscale.
  • Multi-tenant ready: connection-by-user, tenant gate opzionale via metadata standard WUIC.

Flusso end-to-end (esempio: vendita)

  1. Anagrafiche

    Inserisci cliente, prodotti, listini, banche, codici IVA, unità di misura.

  2. Preventivo

    Crea preventivo con righe; trigger tr_preventivi_totali ricalcola imponibile/IVA/totale; può evolvere a ordine via stored sp_converti_preventivo_a_ordine.

  3. Ordine

    Workflow opzionale per approvazioni multi-step. Trigger tr_ordini_scadenze_auto genera scadenze previste in base al pagamento del cliente.

  4. DDT

    Genera DDT da ordine (parziale o totale); trigger movimenta magazzino e marca riga ordine come evasa. Scarico definitivo.

  5. Fattura inviata

    Generata da DDT (fattura differita) o direttamente da ordine (fattura accompagnatoria). Genera XML SDI conforme v1.2; firma CADES‑BES; invio tramite il provider configurato.

  6. Notifiche SDI

    Poller di ritorno riceve ricevute (RC, MC, NS, NE, NV, AT, ...). SdiNotificationApplier traduce in transizioni di stato sull'entità fatture_inviate (es. inviata→accettata). Notifica bell all'operatore.

  7. Scadenze e pagamento

    Le scadenze si attivano allo stato APERTO della fattura. Quando l'incasso arriva (riconciliazione bancaria o input manuale), la scadenza passa a PAGATA tramite sp_marca_scadenze_pagate.

  8. Conservazione sostitutiva

    Job scheduler giornaliero/mensile prende XML + ricevuta SDI, applica timestamp RFC 3161, deposita in Conservazione/AAAA/MM/ (Filesystem) o richiama API InfoCert/Aruba. Index immutable in conservazione_index.

  9. Report fiscali periodici

    Trimestrale LIPE, esterometro mensile (ora abolito ma supportato per retro-compatibilità), CU annuale. XML pronto per upload Fisconline / Entratel.

Installazione

1. Estrazione pacchetto

Scarica FatturazioneElettronica-iis-{version}.zip o FatturazioneElettronica-src-{version}.zip.

  • iis.zip = pubblicazione pronta da estrarre nella physical path IIS (es. C:\inetpub\FatturazioneElettronica).
  • src.zip = staging tree per dotnet publish locale (utile per build custom o deploy linux/docker).

2. Configurazione IIS (Windows)

  1. Application Pool dedicato

    Crea AppPool FatturazioneElettronicaPool:
    • .NET CLR version = No managed code
    • Managed pipeline mode = Integrated
    • Identity = ApplicationPoolIdentity (default) o account di servizio dedicato
    • Start mode = AlwaysRunning (consigliato per scheduler)
    • Idle Time-out = 0 (no idle shutdown)

  2. Site IIS

    • Site name: FatturazioneElettronica
    • Physical path: la cartella estratta dal zip
    • Binding: HTTPS obbligatorio in prod, certificato del dominio aziendale

  3. Permessi NTFS

    L'identity dell'AppPool deve poter scrivere in:
    • Upload\ — allegati e XML SDI in uscita
    • Conservazione\ — output conservazione (per Filesystem)
    • logs\ — log applicativi
    • secrets\ — solo lettura, contiene cert PKCS#12 firma SDI

  4. Modules

    AspNetCoreModuleV2 attivo (installato con ASP.NET Core Hosting Bundle).

3. Deploy linux (alternativa)

Estrai FatturazioneElettronica-linux-{version}.tar.gz in /opt/wuiccore/app/:

bash
sudo tar -xzf FatturazioneElettronica-linux-1.0.0.tar.gz -C /opt/wuiccore/
sudo cp /opt/wuiccore/app/scripts/wuiccore.service /etc/systemd/system/
sudo systemctl daemon-reload
sudo systemctl enable --now wuiccore

Vedi Operations → Deploy per i dettagli (reverse proxy nginx, certificato Let's Encrypt, MariaDB systemd unit).

4. Database

Crea due database SQL Server (o MySQL):

SQL Server
CREATE DATABASE [FatturazioneElettronica_Data];
CREATE DATABASE [FatturazioneElettronica_Metadata];
-- Crea login + user dedicato con db_owner su entrambi (vedi sezione Database)

Lo schema viene popolato al first-run (vedi sotto).

First run

Al primo avvio l'applicazione esegue uno setup wizard guidato che:

  1. Rileva DBMS disponibili (mssql / mysql) in base alle DLL provider presenti
  2. Richiede credenziali DBA per creare/popolare i due DB (dati + metadati)
  3. Esegue gli script dbms/scripts/first-run/{minimal-metadata,tutorial-metadata,tutorial-data}.{mssql,mysql}.sql
  4. Esegue tutti i file dbms/schema/*.sql in ordine alfabetico
  5. Crea l'utente admin/admin di bootstrap (cambia subito la password!)
  6. Setta firstRun=false in appsettings.json

Pre-requisito: AppSettings.firstRun

appsettings.json (parziale)
{
  "AppSettings": {
    "firstRun": "true",        // abilita il wizard
    "dbms": "mssql",            // mssql | mysql
    "meta-dbms": "mssql",
    "preScaffold": "false"
  }
}

Step-by-step

  1. Apri la URL del sito

    https://fatturazione.azienda.it/ — sei re-indirizzato al setup wizard.

  2. Connessione DBMS

    Server, porta, utente DBA, password DBA. Il wizard verifica la connessione e crea i 2 DB se non esistono.

  3. Script bootstrap

    Selezione minimal-metadata + tutorial-data (consigliato) oppure solo minimal (per produzione vergine senza dati esempio).

  4. Account amministratore

    Email, password, dominio. Memorizza la password — non è recuperabile senza reset DB.

  5. Restart automatico

    L'app si riavvia per applicare firstRun=false. Reload del browser → login con account creato.
Importante: se il wizard fallisce a metà (es. timeout connessione DB), droppa i due database e riavvia. Lo script di bootstrap NON è idempotente — eseguirlo due volte produce duplicate-key.

Trigger automatici

Lo schema definisce ~22 trigger che mantengono coerenza fra righe e testate:

  • Totali documenti: ogni INSERT/UPDATE/DELETE su *_righe ricalcola imponibile/IVA/totale sulla testata.
  • Scadenze auto: tr_fatture_inviate_scadenze_auto genera scadenze in base a pagamento_id e data_emissione quando la fattura passa a stato APERTO.
  • Conservazione index: conservazione_index è append-only (no UPDATE/DELETE permessi) — i trigger bloccano le mutazioni per garantire la sealed-log property.

Configurazione · Firma CADES‑BES

Tutte le fatture inviate allo SDI devono essere firmate digitalmente in formato CADES‑BES (PKCS#7 firmato, estensione .p7m). FatturazioneElettronica usa CadesBesSigner basato su BouncyCastle.

Certificato produzione (qualificato AgID)

  1. Acquisisci un certificato di firma qualificato da una CA riconosciuta (Aruba, InfoCert, Namirial, Sielte, Poste, Trust Italia).
  2. Esportalo in formato PKCS#12 (.p12 o .pfx) con la sua catena di certificati e la chiave privata. La password di export protegge il file.
  3. Copialo in FatturazioneElettronica/secrets/sdi-prod-cert.p12 (permessi read-only per l'identity dell'AppPool).
  4. Configura in appsettings.json:
appsettings.json
{
  "Sdi": {
    "Signer": {
      "Pkcs12Path": "C:\\path\\to\\sdi-prod-cert.p12",
      "Pkcs12Password": "__SET_SIGNER_PASSWORD__",
      "SignatureAlgorithm": "SHA256withRSA"
    }
  }
}

Certificato dev/test (self-signed)

Solo per Mock provider: self-signed → SDI reale rifiuta con EC02. Usare solo con MockSdiProvider per testing locale.
PowerShell
cd C:\src\Wuic\FatturazioneElettronica
pwsh -File scripts/generate-dev-sdi-cert.ps1 `
     -OutputPath secrets/sdi-dev-cert.p12 `
     -Password   "wuic-dev-sdi-cert" `
     -ValidYears 5

Configurazione · Conservazione sostitutiva

Per legge le fatture elettroniche devono essere conservate a norma per 10 anni con timestamp RFC 3161 e firma. FatturazioneElettronica implementa 3 provider:

Provider Filesystem (locale, default)

Output in FatturazioneElettronica/Conservazione/AAAA/MM/: XML originale + ricevuta SDI + meta JSON (denominazione, P.IVA, data, sha256, …) + timestamp RFC 3161 (.tsr) ottenuto da una TSA pubblica (Aruba TSA gratuita di default).

appsettings.json (estensione consigliata)
{
  "Conservazione": {
    "Provider": "Filesystem",
    "BasePath": "C:\\FatturazioneElettronica\\Conservazione",
    "TsaUrl": "https://servizi.arubapec.it/tsa/ngrequest",
    "TsaTimeoutSeconds": 30
  }
}

Provider InfoCert

Conservazione delegata a InfoCert (servizio LegalDoc). Richiede contratto attivo con InfoCert e API key:

appsettings.json
{
  "Conservazione": {
    "Provider": "InfoCert",
    "InfoCert": {
      "ApiKey": "__SET_INFOCERT_APIKEY__",
      "ApiSecret": "__SET_INFOCERT_APISECRET__",
      "Endpoint": "https://api.infocert.it/legaldoc/v2",
      "VaultId": "azienda-fe-vault-001"
    }
  }
}

Provider Aruba

Conservazione delegata ad Aruba (servizio DocFly):

appsettings.json
{
  "Conservazione": {
    "Provider": "Aruba",
    "Aruba": {
      "Username": "azienda_docfly",
      "Password": "__SET_ARUBA_DOCFLY_PASSWORD__",

Index immutable

Tutte le conservazioni effettuate sono tracciate in conservazione_index (append-only, no UPDATE/DELETE). Questa tabella è la prova legale dell'avvenuta conservazione: ogni riga contiene hash sha256 del contenuto + timestamp + provider usato + identifier esterno (per InfoCert/Aruba).

Fattura ricevuta

Route #/fatture_ricevute/list. Le fatture arrivano da 3 canali:

  • SDI — il poller di ricezione le inserisce automaticamente in fatture_ricevute con stato RICEVUTA_DA_SDI.
  • Upload XML manuale — admin carica file .xml o .p7m (validato XSD, righe importate).
  • Inserimento manuale — utile per fatture cartacee recuperate (es. contabilità pregressa).

Invio SDI — flusso operativo

  1. Fattura BOZZA_SDI

    L'operatore crea/edita la fattura. Tutti i campi obbligatori FatturaPA devono essere valorizzati (P.IVA cliente, indirizzo, codice destinatario o PEC, aliquota IVA per riga).

  2. Validate

    Click su Valida XML (toolbar): genera XML server-side, valida contro Schema_VFPR12.xsd. Se ok → stato VALIDATA; se errori → dialog con lista, fattura resta in BOZZA_SDI.

  3. Firma + invio

    Click su Invia SDI (row action): pipeline SdiSubmissionPipeline:
    1. Carica XML
    2. Firma CADES-BES con cert PKCS#12 → produce .p7m
    3. Invio al provider configurato
    4. Salva submission_id in fatture_inviate.sdi_submission_id
    5. Stato → IN_INVIO

  4. Ricezione RC (ricevuta consegna)

    Poller di ritorno riceve la RC entro pochi minuti. SdiNotificationApplier transitiona la fattura a INVIATA. Bell notification all'operatore.

  5. Esito SDI

    Entro 15 giorni il destinatario invia NS (notifica accettazione/rifiuto) oppure scatta DT (decorrenza termini). Stati possibili: ACCETTATA, SCARTATA, DECORRENZA.

  6. Apertura contabile

    Su ACCETTATA o DECORRENZA, transizione automatica a APERTO. Trigger tr_fatture_inviate_scadenze_auto genera le scadenze in base al pagamento del cliente.

Invio massivo

Toolbar action Invia massivo selezionati: applica il flusso 1→3 in sequenza su tutte le fatture selezionate (multi-select grid). Ogni invio è transazionale; gli errori vengono raccolti e mostrati nel summary finale.

Numerazione

  • Per sezionale: ogni sezionale ha sequenza separata annuale
  • Numero = progressivo intero (1, 2, 3, …)
  • NumeroEsterno = stringa "FT/2026/000001" composta da prefisso + anno + padding
  • Gap forbidden: il sistema RIFIUTA inserire fattura n+2 se n+1 non esiste (vincolo civilistico)

Conservazione sostitutiva

La conservazione a norma è eseguita dal task scheduler fe_conservazione_mensile (1° del mese alle 03:00). Per ogni fattura del mese precedente:

  1. Compone payload: XML originale + ricevuta SDI + meta JSON (P.IVA, denominazione, importo, hash sha256, …)
  2. Richiede timestamp RFC 3161 alla TSA configurata
  3. Per provider Filesystem: scrive in Conservazione/AAAA/MM/{numero}.xml + .meta.json + .tsr
  4. Per provider InfoCert / Aruba: chiama API REST/SOAP e ottiene identifier remoto
  5. INSERT (immutable) in conservazione_index con provider + path/identifier + hash + timestamp

Toolbar action Conserva ora sulla griglia fatture: forza la conservazione delle righe selezionate senza aspettare il task notturno. Utile per chiusure intermedie.

Scadenze e pagamenti

Route #/scadenze/list. Le scadenze nascono automaticamente alla transizione di una fattura allo stato APERTO in base al piano di pagamento del cliente (es. 30/60/90 giorni fine mese).

Stati scadenza

  • PREVISTA — generata, in attesa di scadere
  • IN_SCADENZA — scadenza nei prossimi 7 giorni
  • SCADUTA — data scadenza passata, non pagata
  • PAGATA — incasso/pagamento registrato (totale)
  • PARZIALE — pagamento parziale registrato
  • INSOLUTA — flaggata dall'operatore (richiede sollecito o gestione legale)

Registrazione pagamenti

Tre modi:

  1. Manuale — drill su scadenza → tab Pagamenti → INSERT con importo, data, modalità, banca
  2. Da riconciliazione bancaria — il match automatico crea il pagamento (vedi sezione successiva)
  3. Massivo — toolbar action Marca scadenze pagate: usa stored sp_marca_scadenze_pagate con filtri (data limite, cliente, conto banca)

Riconciliazione bancaria

Route #/movimenti_bancari/list. Import movimenti via:

  • CSV banca (formato UNICREDIT / Intesa / generico)
  • CBI/PSD2 via PsdConnector (opzionale, richiede AISP)
  • Inserimento manuale

Match automatico

Il task fe_riconciliazione_bancaria matcha movimenti → scadenze con questa euristica (in cascata):

  1. Match esatto: importo + cliente (per IBAN/causale) + ±5 giorni dalla scadenza
  2. Match per causale: pattern FT 2026/000123 o fatt n. 123 nella causale → matcha la fattura corrispondente
  3. Match parziale: stesso cliente, somma di più scadenze uguale all'importo

I match candidati sono mostrati in UI per conferma operatore (riconciliazione assistita), evitando rischi di match sbagliato.

Backup & restore

Cosa salvare

  1. Entrambi i database (dati + metadati) — backup full giornaliero, log ogni 15 min se SQL Server
  2. Cartella Conservazione/ — i .xml/.tsr sono prova legale, perdita = mancato adempimento
  3. Cartella Upload/ — allegati documenti (DDT firmati, scansioni cartacee, …)
  4. Cartella secrets/ — cert .p12 di firma (necessario per riemetterli identicamente in DR)
  5. appsettings.{Production}.json — config completa (anche le chiavi API)

Esempio policy SQL Server

T-SQL
-- Full nightly
BACKUP DATABASE FatturazioneElettronica_Data
TO DISK = 'D:\Backups\fe_data_full.bak'
WITH FORMAT, COMPRESSION, CHECKSUM;

-- Log ogni 15 minuti
BACKUP LOG FatturazioneElettronica_Data
TO DISK = 'D:\Backups\fe_data_log.trn'
WITH COMPRESSION, CHECKSUM;

Restore in DR

  1. RESTORE DATABASE + RESTORE LOG fino al PIT desiderato
  2. Ripristina Conservazione/, Upload/, secrets/
  3. Aggiorna appsettings.Production.json con i nuovi path/connection string se diversi
  4. Sostituisci/aggiorna licenza WUIC se la macchina ha fingerprint diverso
  5. Restart AppPool / servizio; verifica health check

Troubleshooting

Sintomo: fattura resta in IN_INVIO > 1 ora

  1. Verifica connessione al provider: curl -v {endpoint}
  2. Log logs/sdi-{date}.log: cerca SubmitException
  3. Se errore autenticazione: rigenera token / verifica scadenza credenziali
  4. Se errore timeout: aumenta HttpClient.Timeout nei provider
  5. Forza retry: row action Re-invia SDI sulla fattura

Sintomo: fattura SCARTATA con errore EC02 (firma non valida)

  • Verifica Sdi.Signer.Pkcs12Path punta al cert qualificato, non al dev-cert
  • Cert scaduto? Controlla con openssl pkcs12 -in cert.p12 -info -noout
  • Password .p12 errata? Errore di firma lato server prima dell'invio (log: CadesBesSigner: invalid password)

Sintomo: scheduler task non parte

  1. Controlla Scheduler.Enabled = true in appsettings
  2. Query SELECT * FROM scheduler WHERE enabled=1 → task presente?
  3. Query SELECT TOP 20 * FROM scheduler_execution ORDER BY started_at DESC → ultima esecuzione?
  4. Log logs/scheduler-{date}.log per errori specifici

Sintomo: dashboard non si renderizza

  1. F12 console browser → errori JS?
  2. License con feature dashboard-designer? curl /api/Meta/AsmxProxy/MetaService.getLicenseStatus
  3. Metadata cache stale? Eseguire /api/Meta/AsmxProxy/MetaService.invalidateMetadataRuntime

Sintomo: poller SDI duplica notifiche

  • Verifica sdi_provider_cursor: una riga per provider con last_id/last_timestamp valorizzati
  • Se vuota o reset: il poller riparte da zero. UPDATE manualmente il cursor se serve.

FAQ

Quale provider SDI scegliere?

Per piccole-medie aziende (< 500 fatture/anno) e PEC già attiva: DirectPec è la scelta più economica e l'unica completamente gratuita (a parte la PEC). Per volumi alti (> 1000 fatture/anno) o per chi vuole un SLA contrattuale, valutare ArubaPec o FatturePEC per la dashboard di monitoring integrata e supporto dedicato.

Posso cambiare provider SDI senza perdere lo storico?

Sì. Lo storico è in DB ed è provider-agnostico. Disabilita la vecchia sottosezione e abilita la nuova in appsettings.json, poi restart. Le fatture IN_INVIO non ancora finalizzate vanno re-inviate manualmente con il nuovo provider.

Cosa succede se cambio P.IVA aziendale?

Cambio di P.IVA richiede: (1) aggiornamento anagrafica azienda, (2) nuovo certificato CADES con la nuova P.IVA in commonName, (3) eventuale nuovo contratto con provider SDI / conservazione. Le fatture già emesse non si toccano: P.IVA storica resta valida per la fatturazione retroattiva.

Come gestire il passaggio di anno fiscale?

Le sequenze documenti sono per (sezionale, anno). Al 1° gennaio:

  1. Il primo INSERT del nuovo anno crea automaticamente la nuova sequenza partendo da 1
  2. Verifica eventuale gap dell'anno passato (esistono fatture sequenza N+1 senza N?) — il sistema lo blocca a runtime ma controllo formale è buona pratica
  3. Genera LIPE 4° trimestre / Esterometro / CU dell'anno passato entro le scadenze legali
  4. Esegui job di conservazione massiva per chiudere l'archivio dell'anno

Posso usare l'app multi-azienda?

Sì, con due approcci:

  • Multi-tenant per DB: un'istanza app, una coppia DB (dati+metadati) per azienda. Connection-by-user assegna l'utente al tenant.
  • Multi-tenant per riga: un'istanza app, un DB condiviso con colonna tenant_id su tutte le entità. Richiede custom tenant gate (vedi skill app-creation).

Come integro un sistema gestionale esterno?

Tre canali:

  • REST AsmxProxy: POST /api/Meta/AsmxProxy/MetaService.updateRecord per inserimento programmatico documenti. Autenticazione via cookie k-user dopo login.
  • OData: GET /odata/clienti?$filter=... per export dati. Endpoint read-only di default; mutazioni via AsmxProxy.
  • Import CSV/XML: route #/import/list + endpoint POST /api/Conversioni/ImportXml per upload massivo.
